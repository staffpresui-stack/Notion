# Notion接続確認とサンプル3件の取り込み

GASの実行はユーザーが行います。開発環境でのテストはHTTPスタブだけを使い、実Notionへのアクセス・書き込みは行っていません。

## 確認済みの前提（ユーザー報告）

- 旧staff.presuiのGASで検証済みです。以後はfinance@premiere-mode.co.jpの本体GASを使います。重複防止記録はプロジェクト間で自動共有されません。移行方法は `docs/SHARED_DRIVE_TEST.md` を参照します。
- トークンは「MTG議事録連携（GAS）」のものです。コードからインテグレーション名は判定しません。
- 管理用ページ：`400ca178-7419-80e8-bb9a-f157874b6105`
- MTG議事録（テスト）：`d9cc47f9-543e-4bcb-8ec8-27bebc0feac5`
- プロジェクト・タスク（テスト）：`c908936a-6999-4119-9e9c-df364f5f5d1b`
- `setupTestDatabases()` はユーザー側で成功済みです。今回の作業で再実行する必要はありません。
- テスト用タスクDBの「ステータス」は手動追加予定です。status型、未着手／保留／進行中／対応不要／完了を用意します。

## 1. 最新コードへ置き換える

GitHubのworkブランチから `dist/gas-core/Code.gs` をダウンロードしてテキストエディタで開き、GASの「コード.gs」を全文置き換えて保存します。
個別のsrcファイルと一括版を重複して貼らないでください。
この2関数は `UrlFetchApp` とスクリプトプロパティ・ロックだけを使います。Drive・Calendar・Chatworkの設定は不要です。
明示的にOAuthスコープを管理している場合は `https://www.googleapis.com/auth/script.external_request` が必要です。

## 2. 読み取り専用の接続確認

GASのプロジェクト設定で以下を確認します。秘密値はチャットやGitに貼りません。

| プロパティ | 値 |
|---|---|
| ENV | `test` |
| DRY_RUN | `true` |
| SETUP_CREATE_TEST_DB | `false` のまま |
| NOTION_TOKEN | 「MTG議事録連携（GAS）」のシークレット |
| NOTION_DB_MINUTES_TEST | `d9cc47f9-543e-4bcb-8ec8-27bebc0feac5` |
| NOTION_DB_TASKS_TEST | `c908936a-6999-4119-9e9c-df364f5f5d1b` |

関数 **`checkTestEnvironment`** を選び、実行します。

テスト用2DBと管理用ページ直下の「tl;dv 受信」DBを読み、項目名・型とSPECの差分一覧をログに出します。
tl;dv受信DBは子ブロックをページネーションし、名前の完全一致で探します。0件・複数件・アクセス失敗なら取得失敗として報告し、自動作成しません。
ログに出た `NOTION_DB_TLDV_INBOX = ...` のIDを、同名のスクリプトプロパティへユーザーが保存します。この関数は設定もNotionも変更しません。

SPEC 9-2・9-3の項目名・型、事業部領域6択、タスクのステータス5択、6章の受信項目・取り込み状態4択との差を表示します。
タイトルプロパティの名称はtl;dv側で変わり得るため型で確認します。AIメモ・文字起こしは本文で提供される場合があり、欠落は「本文での提供可・要確認」と表示します。本文の実解析はまだ行いません。
依頼者の型など未決事項は参考扱いです。追加項目も一覧に表示します。差分を自動修正しません。

## 3. DRY_RUNでサンプルを確認

`ENV=test`、`DRY_RUN=true` のまま **`ingestFixturesToNotionTest`** を実行します。

- 埋め込み済みの判定JSON3件を処理します。Driveの読み取りは不要です。
- 社内・高：確認待ち、社外・高：確認待ち、社外・低：仕分け待ちが想定です。
- 規則判定、食い違い、格納予定、送信予定のNotionペイロード、書き込まないタスク提案をログに出します。
- Notionのページ作成、設定・重複防止記録への書き込みは行いません。
- 議事録DBの必須項目名・型が違う、関連するプロジェクトがテスト用タスクDSを指していない場合は、作成前に停止します。

参照候補のPJページはGETで所属を確認します。テスト用タスクDBにない・アクセスできない・アーカイブ済みなら関係を空にしてログに出します。未登録PJの除外はSPEC 8章の格納先の食い違いとは区別し、確認待ちを仕分け待ちへ変える理由にはしません。
存在しない事業部領域や6択以外の値は送信しません。Notionの選択肢を増やすリクエストは送りません。

## 4. テスト用Notionにページを作成

DRY_RUNの内容を確認後、**`DRY_RUN=false`** に変更し、同じ **`ingestFixturesToNotionTest`** を実行します。

`ENV=test`、報告済みのテストDBのID、管理ページ配下・データソース所属の照合が通ったときだけ、MTG議事録（テスト）に最大3ページを作ります。
確認済みIDをコードにも固定しているため、プロパティを本番IDや別のDBのIDへ変えても書き込めません。変更が必要ならコードの変更と再検証を行います。
本文はサンプルの基本情報、summaryの決定事項・ネクストアクションです。録画・Drive・tl;dvのURLは本文に載せず、MTG URLプロパティはこのサンプル機能では空にします。
NotionユーザーID不明の参加者はpeopleを空にし、本文へ名前を入れます。
判定状態・格納予定はログに出します。SPECにない状態プロパティは追加せず、実Drive配置も行いません。タスクの作成・更新、Chatworkへの通知も行いません。

終了したら **`DRY_RUN=true` に戻してください**。これはサンプル機能だけのテスト用書き込み許可であり、本番運用への切替ではありません。
この2関数は独立した設定検査を使います。既存の全体用 `checkConfig()` は通常のDRY_RUN設定を要求するため、今回の実行順には含めません。

## 重複防止と失敗時

同じGASプロジェクトのスクリプトプロパティに、テストDB・meeting_keyごとの記録を保存します。
キーは `NOTION_FIXTURE:<テスト議事録DBのハイフンなしID>:<meeting_key>` です。

- 作成前に `pending` を保存し、成功後は `created` とページIDを保存します。
- 作成済みなら再実行でスキップし、ページIDをログへ出します。
- 通信中断やAPIエラーで結果が不明なら `pending` を残し、自動再作成しません。
- pendingの場合はNotionとログを確認し、作成済みなら `{ "state": "created", "pageId": "実際のページID" }` をその記録に設定します。未作成を確認できた場合だけ該当pending記録を削除して再実行します。確認なしに記録を消さないでください。
- 同一プロジェクト内の多重実行はロックで抑止します。別のGASプロジェクトでは記録を共有しません。同じサンプルを別プロジェクトで並行実行しないでください。
- 取り込みに失敗したケースは結果が「要対応」となり、他のケースの処理は継続します。

## ローカル検証と埋め込みデータ

```sh
npm run build
npm run check
npm test
npm run smoke
```

buildはfixturesから `gas-core/src/notionFixtures.generated.js` を再生成し、distへまとめます。判定JSON3件・mastersは提供ファイルと同じです。
提供されたmanifestは社外・高の1件だけのため、社内・高とtl;dvの2件は `fixtures/notion_test_manifests.json` に検証専用データを補完しました。実会議の情報ではありません。
HTTPスタブによるテストで、dry-run無書き込み、再実行・中断時の重複防止、テストDB制限、選択肢除外などを検証します。
